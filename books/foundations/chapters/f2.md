# LLM basics in plain words
> lead: What an LLM actually is, what tokens, context windows and embeddings mean, and why a model remembers nothing, explained with the instructor's analogies before any agent code appears.
meta: Foundations | Classes 03 to 05 | 15 min read

## Why it matters

Every later topic (cost, memory, RAG, guardrails) is a consequence of a few basic facts about how models work. If these are clear, the rest reads as common sense instead of jargon.

## Core ideas

### LLM calls are stateless

:::key The model remembers nothing
Each API call takes an input and returns an output. A chat app only *looks* like it remembers because it **resends the whole conversation on every message**. Memory is something you build around the model.
:::


**Five terms to know before building an agent** (from the class-03 write-up): an LLM predicts the next *token*, not the next word; tokens are the billing currency and output costs more than input; embeddings put similar meaning close together; the context window is a whiteboard of fixed size; parameters are billions of weights fixed at training time, not the same thing as tokens.

- **Three message roles.** The system message ("You are a helpful assistant...") is optional but good practice, and it is **resent on every call** because the model is stateless. Sending a single "hi" still transmits system plus user plus the assistant reply so far, which you can see in a raw request payload.
- **Knowledge cutoff.** Every model card lists a cutoff date; a raw model cannot browse, so asked about yesterday's match it admits it cannot know. A web app can browse only because it layers search on top. This is exactly why agents need tools.
- **Web app versus API.** A web subscription is an all-you-can-eat buffet (flat price, usage not shown per token); the API is à la carte (pay per token, full transparency). OpenRouter gives one key for models from every major provider, with the exact input and output token counts visible in its dashboard.

## What the AI terms site adds beyond the table

*From a full read of all 21 pages of the instructor's AI terms site. The table above has the one-liners; these are the extra points each page makes.*

- **LLM:** asked "the capital of France is", the model is not looking up a table; it is computing that "Paris" is overwhelmingly the most likely next word.
- **Tokens:** every price you see is counted in tokens, so a long unusual word quietly costs more than it looks. "Unbelievable" splits into three pieces.
- **Embeddings:** once meaning is a location, the distance between two ideas is measured the way a map measures distance between cities ("dog" and "puppy" near, "dog" and "spreadsheet" far).
- **Context window:** "why did it forget what I said three messages ago" is the whiteboard filling up, not carelessness.
- **Parameters:** a "70-billion-parameter model" is a slider count, a rough proxy for capacity, never a guarantee of a good answer.
- **Attention:** the same word means different things depending on neighbours ("bank" with "deposited" locks onto money), computed for every word against every other, all at once.
- **Transformer:** LLM and Transformer are not the same thing; the Transformer is the architecture (stacked attention layers) that makes next-word prediction possible. Early layers catch obvious relations; deeper ones catch tone and implication.
- **Training:** hidden text with the real text as its own answer key, so no human labels are needed, which is what makes training at scale affordable.
- **Fine-tuning:** a focused residency after a general degree. It teaches what not to say too, including training out confident guessing.
- **RLHF:** humans pick the better of two answers and that nudges future behaviour. Caveat from the site: raters may reward a confident, pleasant tone over an honest "I'm not sure".
- **Prompting:** zero-shot has no examples; few-shot shows two or three worked examples and makes output much more consistent.
- **Temperature:** low for facts, data extraction, code and numbers; higher for brainstorming and creative writing.
- **Hallucination:** the model has nothing inside that separates "I know this" from "this sounds plausible", and the matching tone is the danger. Double-check anything that matters.
- **RAG:** only as good as what is retrieved. Pulling the wrong document, common when the query is worded differently from the source, makes the model confidently build on the wrong foundation.
- **Context engineering:** sits above prompting and RAG. It is why an assistant seems to remember you across sessions even though each message starts from a blank page.
- **MCP:** the USB-C idea, one standard port for every tool.
- **Agents:** the difference is not intelligence, it is whether the AI has hands or just a mouth.
- **Multimodal, reasoning models, small models, AGI vs ASI:** more senses; a trained step-by-step thinking stage before the answer (the "thinking..." pause is real reasoning, not an animation); a distilled specialist that is faster and cheaper; and two theoretical levels (matching, then exceeding humans) that do not exist today.

## What AI costs: subscription versus API

*From the instructor's guide "AI Web vs. API Economics" (read in full). Its figures are reported 2026 industry numbers, quoted as the guide gives them; check current prices before budgeting.*

**Buffet versus à la carte.** A chat subscription (Claude Pro, ChatGPT Plus) is a buffet ticket: one flat price, one human, one seat, fair-use limits. The API is à la carte: you pay for exactly what you order, and software can order, not just people. Three reasons a $20 login cannot power your app: the licence is for a human in a browser, flat pricing assumes humans pause while software does not, and the providers' terms separate the chat app from programmatic access.

**Design it versus run it.** You can ask Claude in a normal chat to design an n8n workflow or write code. The moment it must run unattended (on a schedule, on a webhook), it needs its own API key.

**The ladder.** Asking a question fits the subscription. A chat widget on your site, an automated support agent, or a full agentic system needs the API.

**Why bills surprise people: the multiplication, not the price.**

- The API is stateless, so every turn resends the whole conversation, plus the system prompt and tool definitions, plus raw tool results, plus any retry. A demo with one message is the cheapest possible use.
- The guide reports: an agent handling a request costing about $1.20 in 2026 versus about $0.04 for a 2023 chatbot reply; agentic tasks using on the order of 1,000 times the tokens of a simple reply; and 73 percent of enterprises exceeding their AI budget while per-token prices fell. Falling price per token and rising total spend are not a contradiction.
- Its case study: Uber reportedly spent its 2026 AI budget in about four months after rolling out token-billed coding tools to roughly 5,000 engineers, then capped spending per employee per tool.

**Model pricing.** Prices are per million tokens, billed separately for input and output. The guide's July 2026 table spans about 71 times on input price between the cheapest open-weight model and the most expensive premium one, in four tiers: premium (frontier reasoning), mid-tier, budget (classification, extraction, routing: the workhorse for high volume) and open-weight.

**Open and self-hosted.** Cheaper open-weight models can be called through a low-cost API or run on your own hardware. Self-hosting trades a metered bill for GPUs, engineers and uptime; the guide puts the crossover in the tens of millions of tokens a month for budget models, lower for premium ones. Data that legally cannot leave the building is another reason.

**Three questions to choose.** Does a person click send every time? Could it run thousands of times a day? Tens of millions of calls a month? Real projects mix all three: a subscription for team chat, an API for the customer bot, an open model for the highest-volume low-stakes task.

:::trap Do not confuse the two products
A subscription login is not an API key. Using a consumer login to drive your own app is outside what it is licensed for.
:::

## Open-source and open-weight models

*From the instructor's guide "Open Source AI" (read in full). Benchmark figures are the guide's 2026 snapshot and shift with every release.*

**Two separate questions.** Free versus paid is about money. Open versus closed is about whether the trained model itself is published for anyone to download. They are independent: Claude Pro is paid and closed, a free chatbot tier is free and closed, and an open model can be run by you for free or by someone else for a fee.

**What "open" means.** Open-weight means the trained parameters are released. Licences differ: some (Apache 2.0, MIT) have no real restrictions on use or selling products; others (the guide puts Llama 4 here) add rules; check the licence before shipping commercially.

**Where models live.** Hugging Face is the shared public library for models, with model cards describing what each does. Ollama's library and LM Studio's search are friendlier windows into it.

**Closing the gap.** The guide reports the best open models trail the closed frontier by months, not years, on many benchmarks, and that closed models still hold an edge on the hardest reasoning, multimodal and safety-critical work.

**Running one yourself.** Ollama (command line; `ollama pull` then `ollama run`) and LM Studio (a graphical app) both run models on your computer through the same engine, `llama.cpp`, and expose a local server (the guide gives `localhost:11434` for Ollama), so a local model answers like any other API.

**Model size and memory.** Size is in billions of parameters (7B, 32B, 70B); bigger needs more memory. A graphics card speeds things up a lot, and a plain laptop can run smaller models slowly.

**Quantization.** Rounding a model's numbers to be less precise shrinks the file a lot for a small quality loss. Most local models are quantized; the tools pick a sensible default.

**Why companies do it.** Security (nothing leaves your machine; works air-gapped), cost at volume, and speed (no network round trip). **Honest trade-offs:** you own maintenance and updates, hardware costs money up front, the closed frontier still leads at the very top, and you build the guardrails and polish yourself. Many real systems route routine high-volume work to an open model and keep a frontier model for the hard questions.

**Three questions to choose a path.** Is the data sensitive or regulated? Is the volume high? Does the task need the single best reasoning available?

## Interview corner

:::qa Why can a $20 subscription not power my app?
It is licensed for one human in a browser, flat pricing assumes humans pause, and providers' terms separate the chat app from programmatic access. Apps use the metered API instead, where cost grows with the tokens you send, including the whole conversation resent each turn.
:::

:::qa Why do LLMs need memory added to them?
Each API call is stateless. The app stores the messages and sends the **full history** on every call, so the model can use earlier turns.

**Follow-up to expect:** "What is the cost of that?" Tokens grow with every turn, which is why later chapters cover trimming and summarising history.
:::

## Common mistakes

| Mistake | Symptom | Fix |
| --- | --- | --- |
| Assuming the model remembers earlier calls | It "forgets" what you said | Resend the history yourself on every call |
| Treating tokens as words | Surprise bills on long or unusual text | Count tokens; output costs more than input |
| Trusting a fluent answer | A confident wrong fact | Treat fluency as no evidence of truth; retrieve or verify |
