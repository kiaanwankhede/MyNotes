# Validators
> lead: Write your own rules: field validators for one field, model validators for rules across fields, in four modes, with a fixed order of execution.
meta: Pydantic | Docs "Validators", class 03, the notebook | 20 min read

## Why it matters

Built-in constraints cover most cases. Business rules ("a disposable email is not allowed", "password must equal confirm_password") need code.

## Core ideas

### field_validator: one field

It sees one field's value and nothing else. Return the value (cleaned or not) to accept, or raise `ValueError` to reject. Raise `ValueError` or `AssertionError`, not `ValidationError`: Pydantic turns those into entries in its single error. (`AssertionError` checks vanish if Python runs with `-O`; `PydanticCustomError` gives the most control over the message.)

```python
from pydantic import BaseModel, EmailStr, field_validator

class JobApplication(BaseModel):
    email: EmailStr

    @field_validator("email")
    @classmethod
    def no_disposable(cls, value: str) -> str:
        if value.split("@")[-1].lower() in {"yopmail.com", "mailinator.com"}:
            raise ValueError("disposable email domains are not accepted")
        return value.lower()
```

### Four modes of field validator

| Mode | Runs | Notes |
| --- | --- | --- |
| **after** (default) | After Pydantic's own validation | The value already has the right type |
| **before** | On the raw input, before parsing | Use `Any` as the hint; good for cleaning `"5 years"` to `5` |
| **plain** | Replaces Pydantic's validation | Later validators and the type check are skipped, so bad input can pass |
| **wrap** | Around Pydantic's validation, with a `handler` | Can run code before and after, catch errors, retry with other input, or skip the handler |

:::trap The notebook's "strip years" validator
In the notebook, `strip_years_suffix` says it runs "BEFORE the int type-check" to turn `"5 years"` into `5`, but it is declared without `mode="before"`. The default is **after**, so by then Pydantic has already rejected `"5 years"` as not an int and the validator never sees it. Add `mode="before"` for the behaviour its docstring describes.
:::

### model_validator: rules across fields

The class posed the problem: an applicant with an `@infosys.com` email needs at least 5 years of experience. A field validator cannot do it, because it sees one field at a time (the class called it "Schrödinger's field"). A model validator sees the whole model.

```python
from pydantic import BaseModel, model_validator

class SignupForm(BaseModel):
    password: str
    confirm_password: str

    @model_validator(mode="after")
    def passwords_match(self):
        if self.password != self.confirm_password:
            raise ValueError("passwords do not match")
        return self
```

Model validators also have **before** (a classmethod receiving raw input, which may not be a dict) and **wrap** modes. An after-validator is an instance method and must return `self`.

:::key Fixed order
Every field validator runs first, for every field. Then the model validator runs on the fully validated object. (Class 03.) Within one field, `before` and `wrap` validators run right to left, then `after` validators run left to right.
:::

### Validators that need more context

A validator can take an optional `ValidationInfo` argument. It carries `data` (fields already validated, so only earlier fields), a user-supplied `context`, the `mode`, and the `field_name`. Pass context with `Model.model_validate(data, context=...)`; plain `Model(...)` cannot take it.

### Reusable validators

With the Annotated pattern, `AfterValidator(fn)` and friends attach to a type, so you can define something like an "even number" type once. With the decorator, one function can target several fields, or all of them with `'*'`.

### `validate_call`: validating function arguments (from the Validation Decorator page)

:::note Source
Pydantic docs, [Validation Decorator](https://pydantic.dev/docs/validation/latest/concepts/validation_decorator/), read on 31 Oct 2026 from the docs source on GitHub, which tracks the main branch (text and tables read; long code samples skimmed).
:::

`@validate_call` checks a function's arguments against its type hints before the function runs, using the same machinery as models. It works with positional, keyword-only, positional-only, `*args` and `**kwargs` parameters (and `Unpack` of a `TypedDict` for `**kwargs`, v2.10).

- Types come from the annotations (`Any` if missing) and are **coerced** as elsewhere: a date string becomes a `date`. Pass `config=ConfigDict(strict=True)` for strict mode.
- The return value is **not** validated unless you set `validate_return=True`.
- `Field()` works on parameters, best in the `Annotated` form, including aliases.
- `raw_function` gives the undecorated function for trusted inputs. Async functions work. Type checkers keep the signature but will not see `raw_function`.
- Failure raises the standard `ValidationError`, including for missing arguments (Python would raise `TypeError`).
- To validate arguments now and call later, return an inner function from a decorated outer one.

### The experimental pipeline API (from the Experimental page)

Since v2.8 an experimental `validate_as` pipeline composes validation, transformation, constraints and predicates in a type-safe chain (steps joined with `|` or `&`). It is a typed alternative to `BeforeValidator`, `AfterValidator` and `WrapValidator`, and may change or be removed. The docs themselves advise plain code (separate `UserIn` and `UserOut` models) unless the saving is significant.

### From V1: validators

`@validator` and `@root_validator` are deprecated in favour of `@field_validator` and `@model_validator`. There is no `each_item`; annotate the item type instead (`list[Annotated[int, Field(ge=0)]]`). A `TypeError` raised in a validator is **no longer** turned into a `ValidationError`. `allow_reuse` is no longer needed, and `@validate_arguments` is now `@validate_call`.

## Common mistakes

| Mistake | Symptom | Fix |
| --- | --- | --- |
| Forgetting to return the value | The field becomes `None` | Always return the (cleaned) value |
| Reusing a method name | One validator silently disappears | Give each a unique name |
| Cross-field rule in `field_validator` | Cannot see the other field | Use `model_validator` |
| Raising `ValidationError` yourself | Wrong error type | Raise `ValueError` |
| Cleaning raw text in an `after` validator | Never reached | Use `mode="before"` |

## Interview corner

:::qa field_validator versus model_validator?
The first checks one field with no view of the others. The second sees the whole model after every field check has passed, so it handles cross-field rules.
:::

:::qa What does mode="before" do, and when do you need it?
It runs on the raw input before type coercion, so you can clean messy input before Pydantic tries to read it. Without it, the validator only sees an already-valid value.
:::

:::qa What is the difference between a plain and a wrap validator?
A plain validator replaces Pydantic's check entirely, so invalid input can slip through. A wrap validator calls Pydantic's check through a handler and can catch errors or retry.
:::
