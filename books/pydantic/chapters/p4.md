# Computed fields and controlling output
> lead: Derive values instead of storing stale ones, and decide exactly which fields leave a model.
meta: Pydantic | Part 4 | 8 min read

## Why it matters

Some values should always be calculated from others, and almost every real API must hide or trim fields. Both are one-line settings.

## Core ideas

### @computed_field

Stack `@computed_field` on a `@property`. The value is read-only, appears in `model_dump()` and the JSON schema, and is recomputed on every access, so it never goes stale.

```python
from pydantic import BaseModel, computed_field

class Application(BaseModel):
    years: int

    @computed_field
    @property
    def tier(self) -> str:
        return "junior" if self.years < 2 else "mid" if self.years < 7 else "senior"
```

:::analogy The receipt total
A receipt total is not typed in; it is added up at checkout, so a changed price is reflected on the next receipt. `computed_field` is that adding-up.
:::

:::tip Do the arithmetic in code, not in the LLM
Models are unreliable at consistent arithmetic. Let the model classify (for example a priority), then derive numbers such as an SLA with a `computed_field`.
:::

### Dump control

| Flag | Effect |
| --- | --- |
| `exclude={"password"}` | Remove named fields |
| `include={"username"}` | Only these fields |
| `exclude_none=True` | Drop fields currently `None` |
| `exclude_unset=True` | Keep only fields the caller actually set; the one for PATCH-style partial updates |

## Common mistakes

| Mistake | Symptom | Fix |
| --- | --- | --- |
| Storing a derived value | It drifts out of sync | Use `computed_field` |
| PATCH that dumps defaults | Overwrites other data with defaults | `model_dump(exclude_unset=True)` |

## Interview corner

:::qa Why exclude_unset for PATCH?
It serialises only what the caller explicitly provided, so unset defaults do not silently overwrite stored values.
:::
