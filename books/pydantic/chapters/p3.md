# Constraints and custom validators
> lead: Types are not enough: use Field() for ranges and patterns, special types for emails and secrets, and validators for your own business rules.
meta: Pydantic | Part 3 | 15 min read

## Why it matters

`age: int` accepts `-50`. Real rules (minimum length, a range, a format, "these two fields must agree") need constraints and validators.

## Core ideas

### Field() constraints and Annotated

Numbers take `gt, ge, lt, le`. Strings take `min_length, max_length, pattern`. The `Annotated[int, Field(gt=0, le=120)]` form separates the type from its metadata and is preferred in production code; the direct `age: int = Field(gt=0, le=120)` form behaves the same.

```python
from typing import Annotated
from pydantic import BaseModel, Field

class Applicant(BaseModel):
    name: Annotated[str, Field(min_length=2, max_length=100)]
    years: Annotated[int, Field(ge=0, le=50)]
```

### Special types

`EmailStr` (needs `pip install pydantic[email]`), `HttpUrl`, and `SecretStr`, which prints as `**********` and gives the real value only through `.get_secret_value()`.

### field_validator: one field

Operates on a single field. `mode="after"` (default) receives the already-coerced value; `mode="before"` receives raw input, useful for cleaning `"5 years"` to `5`. Return the value to accept or raise `ValueError` to reject.

```python
from pydantic import field_validator

class Applicant(BaseModel):
    name: str

    @field_validator("name")
    @classmethod
    def tidy(cls, v: str) -> str:
        if not v.strip():
            raise ValueError("name cannot be empty")
        return v.strip().title()
```

### model_validator: rules across fields

Receives the whole model after every field has passed, so it can check "password equals confirm_password".

```python
from pydantic import model_validator

class Signup(BaseModel):
    password: str
    confirm: str

    @model_validator(mode="after")
    def same(self):
        if self.password != self.confirm:
            raise ValueError("passwords do not match")
        return self
```

:::key Fixed order
Every `field_validator` runs first, for every field. Only then does `model_validator` run.
:::

| Need | Tool |
| --- | --- |
| Check or clean one field | `field_validator` |
| Rule across two or more fields | `model_validator` |
| Compute a new value from others | `computed_field` (next chapter) |

Try it: the playground on the book's start page mirrors these rules.

## Common mistakes

| Mistake | Symptom | Fix |
| --- | --- | --- |
| Forgetting to return the value in a validator | Field becomes `None` | Always return the (cleaned) value |
| Putting a cross-field rule in `field_validator` | Cannot see the other field | Use `model_validator` |
| Logging a plain `str` password | Secret in logs | Use `SecretStr` |

## Interview corner

:::qa field_validator versus model_validator?
The first checks one field with no view of the others. The second sees the whole model after all field checks passed, so it handles cross-field rules.
:::

:::qa What does mode="before" do?
It runs on the raw input before type coercion, so you can clean messy input (like `"5 years"`) before Pydantic tries to read it as an int.
:::
