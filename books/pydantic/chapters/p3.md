# Fields and constraints
> lead: Types are not enough. Field() adds ranges, lengths, patterns, defaults, aliases and more, and Pydantic ships ready-made types for emails, URLs and secrets.
meta: Pydantic | Docs "Fields", class 03, the notebook | 15 min read

## Why it matters

`age: int` accepts `-50` and `10000`. Real rules (minimum length, a range, a format) belong in the model, so the data is checked in one place.

## Core ideas

### Constraints

| Kind | Options |
| --- | --- |
| Numbers | `gt`, `ge`, `lt`, `le`, `multiple_of` |
| Strings and sequences | `min_length`, `max_length`, `pattern` (a regex) |
| Decimals | `max_digits`, `decimal_places` |

```python
from pydantic import BaseModel, Field

class JobApplication(BaseModel):
    full_name: str = Field(min_length=2, max_length=100)
    years_experience: int = Field(ge=0, le=50)
```

On an optional field (`X | None`) the constraint applies to the non-`None` part.

### Field() versus Annotated

Two equivalent styles:

```python
from typing import Annotated
from pydantic import BaseModel, Field

class A(BaseModel):
    years: int = Field(ge=0, le=50)                    # direct

class B(BaseModel):
    years: Annotated[int, Field(ge=0, le=50)]          # Annotated
```

The docs recommend `Annotated` because required fields stay visibly required, you can stack several pieces of metadata, types become reusable, and constraints can target inner items (`list[Annotated[int, Field(gt=0)]]`). The class note says Mayank prefers plain `Field()` for readability but warns that AI-generated code often uses `Annotated`, so you must recognise both. `default`, `default_factory` and `alias` still use normal assignment.

### Defaults

- A plain value, or `Field(default=...)`.
- `default_factory` takes a callable, for example one that makes a new id. Since Pydantic 2.10 it may take one argument, the already-validated data, so fields it reads must be declared earlier.
- Mutable defaults such as a list are copied per instance, so instances do not share state.
- Defaults are **not validated** unless you set `validate_default=True`.

### Aliases

`alias` renames a field for both input and output. `validation_alias` affects only input, `serialization_alias` only output. Output uses aliases only when you call `model_dump(by_alias=True)`.

### Other options

`strict=True` (no coercion for this field), `frozen=True` (cannot be reassigned), `exclude=True` (omitted from `model_dump`), `repr=False`, `discriminator` (choose a union member by a field's value), `deprecated`, and schema-only options `title`, `description`, `examples`.

### Special types

| Type | What it does |
| --- | --- |
| `EmailStr` | Validates email format (needs `pip install "pydantic[email]"`) |
| `HttpUrl` | Validates URLs |
| `SecretStr` | Masks the value in output and logs; read it on purpose with `.get_secret_value()` |
| `PositiveInt`, `NonNegativeInt` | Shortcuts for `gt=0`, `ge=0` |

The class singled out `SecretStr` as underused but important in this course, since API keys are handled constantly. In the notebook, `account.model_dump(mode="json")` is what gets written to a JSON file.

### Aliases in depth (from the official Alias page)

:::note Source
Pydantic docs, [Alias](https://pydantic.dev/docs/validation/latest/concepts/alias/), read in full on 31 Oct 2026.
:::

An alias is an alternative name for a field. There are four ways to set one: `alias`, `validation_alias` (a `str`, `AliasPath` or `AliasChoices`), `serialization_alias`, and `alias_generator` in the config.

- **`AliasPath`** reads a value from inside nested data: `AliasPath('names', 0)` takes `names[0]`, and `AliasPath('contact', 'address')` takes `contact['address']`.
- **`AliasChoices`** accepts several input names; **earlier choices win**. If both `first_name` and `fname` are sent, `first_name` is used. Choices can mix plain names and `AliasPath`.
- **Alias generators** name every field at once. Three are built in: `to_pascal`, `to_camel`, `to_snake`. A plain callable works (`lambda name: name.upper()`), and `AliasGenerator` lets validation and serialization use different generators.
- **Precedence.** An explicit `alias` on a `Field` beats the generator by default. `alias_priority=2` means the generator never overrides it; `alias_priority=1` means the generator does.
- **Config switches.** `validate_by_alias` is `True` and `validate_by_name` is `False` by default; setting both to `False` is an error. `serialize_by_alias` is off by default, and the docs say they expect to change that in V3. The same switches exist per call: `by_alias` and `by_name` on `model_validate`, `model_validate_json`, `model_validate_strings` and `TypeAdapter`, and `by_alias` on `model_dump`, `model_dump_json` (default `False`).

## Common mistakes

| Mistake | Symptom | Fix |
| --- | --- | --- |
| Expecting a default to be validated | Invalid default slips through | `validate_default=True` |
| Using `Field(...)` inside a union on the wrong side | Constraint has no effect | Put the metadata around the whole union |
| A plain `str` for an API key | Key appears in logs | `SecretStr` |

## Interview corner

:::qa Field() or Annotated?
Both work the same. Annotated keeps required fields visibly required and is reusable, which is why the docs prefer it. The class prefers plain `Field()` for readability but wants you to recognise both.
:::

:::qa alias versus validation_alias versus serialization_alias?
`alias` applies to input and output, the other two to only one direction. Output uses aliases only with `by_alias=True`.
:::
