# Reading validation errors
> lead: A ValidationError collects every problem in one pass, and each entry says where, what and why in a form code can read, which is what makes automatic retries possible.
meta: Pydantic | Docs "Error handling" | 8 min read

## Why it matters

The error is not just a message for a human. Its structure lets you show clear feedback to an API caller, or hand the failure back to an LLM so it can correct itself.

## Core ideas

One `ValidationError` bundles **all** errors from a validation pass, not the first one. Ways to read it:

| Call | Gives |
| --- | --- |
| `str(e)` | A readable block per error |
| `e.errors()` | A list of dicts |
| `e.error_count()` | How many |
| `e.json()` | The list as JSON |

Each entry in `errors()`:

| Key | Meaning |
| --- | --- |
| `type` | Machine-readable id such as `missing`, `greater_than`, `int_parsing`, `value_error` |
| `loc` | A tuple: field name first, then nested names or list indexes, for example `('items', 1, 'value')` |
| `msg` | Human-readable message |
| `input` | The value that failed |
| `ctx` | Optional values used to build the message, such as the `gt` bound, or the original exception |
| `url` | A link to the docs for that error type |

```python
from pydantic import BaseModel, ValidationError

class User(BaseModel):
    id: int
    tastes: dict[str, int]
    signup_ts: str            # required, so a missing value is a second error

try:
    User(**{"id": "not an int", "tastes": {}})
except ValidationError as e:
    for err in e.errors():
        print(err["loc"], err["type"], err["msg"])
```

For the get-started example in the docs this reports two problems at once: `id` could not be parsed as an integer, and the required `signup_ts` is missing.

Your own validators raise `ValueError` (or `AssertionError`) and Pydantic turns them into `value_error` entries whose message starts with "Value error,".

### Customising messages

Because every entry has a `type` and `ctx`, you can map types to your own templates (for translation or friendlier wording) and rewrite `loc` into a dotted path like `items[1].value`. The docs show both as small helper functions over `e.errors()`.

:::key Why this matters for LLMs
The same structured list, passed back to a model as text, is the trigger for the retry pattern in chapter 11.
:::

## Common mistakes

| Mistake | Symptom | Fix |
| --- | --- | --- |
| Showing `str(e)` to API users | Noisy, internal wording | Map `type` to your own message |
| Catching a generic exception around validation | Real bugs get swallowed | Catch `ValidationError` specifically |

## Interview corner

:::qa What is in a Pydantic error entry?
`type`, `loc`, `msg`, `input`, and optionally `ctx` and `url`. `loc` is a tuple that includes nested names and list indexes.
:::
