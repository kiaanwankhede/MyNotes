# Where Pydantic goes next, and the final project
> lead: An honest map of the ecosystem above core Pydantic, then a small support-ticket triage service that uses every idea in the book.
meta: Pydantic | Part 9 and final project | 12 min read

## The ecosystem map

This book covers core Pydantic: `BaseModel`, `Field`, validators, `computed_field`, nested models, dump control, settings, and structured output with the OpenAI and Anthropic SDKs.

- **One layer up:** libraries such as Instructor patch an LLM client to validate and retry automatically, which is the retry loop from chapter 8 wrapped in a decorator.
- **Two layers up:** agent frameworks (PydanticAI, LangChain, CrewAI) use Pydantic for tool schemas and structured agent outputs, and add orchestration: when to call a tool, multi-turn state, chaining calls. Orchestration is not Pydantic's job; validating data against a schema is.

:::beyond Out of scope here
PydanticAI, LangChain, CrewAI and Instructor are not taught in this book. LangChain is taught in the next book.
:::

## Final project: support-ticket triage

`POST /triage` takes a messy support message and returns a validated result: category, priority, sentiment, a computed SLA and redacted customer info.

| Piece | Concept used |
| --- | --- |
| `IncomingTicket` | A `mode="before"` `field_validator` redacts email addresses before storing (chapter 3), and it is the FastAPI request body (chapter 7) |
| `TriagedTicket` | `Literal` for category, priority and sentiment (chapter 8); a nested `CustomerInfo` (chapter 5) |
| `sla_hours` | A `computed_field` from priority: high 4, medium 24, low 72 (chapter 4), so the LLM never does arithmetic |
| Safety net | A `model_validator` rejects `high` priority with `general_question` (chapter 3) |
| `AppSettings` | Picks Anthropic, then OpenAI, then a free OpenRouter model, whichever key exists (chapter 6) |

## Common mistakes

| Mistake | Symptom | Fix |
| --- | --- | --- |
| Letting the LLM compute derived values | Inconsistent numbers | Derive them with `computed_field` |
| Assuming a framework replaces understanding | Cannot debug failures | Know the validate-and-retry loop first |

## Interview corner

:::qa How would you design a reliable LLM-backed API endpoint?
Validate and clean the request with a model, ask the provider for a structured response in a `Literal`-constrained schema, derive computed values in code, add a model validator for impossible combinations, and cap retries.
:::
