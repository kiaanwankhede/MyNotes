# Validating what an LLM gives you back
> lead: LLM text output is unreliable. Ask the provider to guarantee a Pydantic schema, constrain values with Literal, and retry with the validation error when it still fails.
meta: Pydantic | Pydantic's LLM article and docs, the instructor's site | 15 min read

## Why it matters

An LLM asked for JSON may add a code fence, a friendly preamble, or return a number as a string. Cleaning that up with string tricks is fragile. Pydantic's own article makes the same argument: model output is untrusted, and a model gives it a defined shape.

## Core ideas

### Three approaches, from simple to robust

The Pydantic article on LLMs walks through them:

1. **Prompt for JSON, then validate.** Ask for a JSON object with given fields and parse the reply with `model_validate_json`. Simple, but replies can arrive wrapped in a markdown fence or surrounded by prose, which breaks parsing.
2. **Tool calling with a generated schema.** Pass `Model.model_json_schema()` as a function's parameters and require the model to call that function. The prompt holds only the data request; the schema defines the structure, including nesting. Note the article's caveat: tool calling was designed to call external APIs, so using it to format output is a repurposing.
3. **A wrapper library.** Instructor wraps the client so you pass a `response_model` and get a validated object back.

Provider SDKs have since added direct support. The instructor's site shows:

| Provider | Call | Result |
| --- | --- | --- |
| OpenAI | `client.responses.parse(model=..., input=..., text_format=Model)` | `response.output_parsed` |
| Anthropic | `client.messages.parse(model=..., max_tokens=..., messages=..., output_format=Model)` | `response.parsed_output` |

The same model works for both; only the SDK call changes. Add `extra="forbid"` so the generated schema rejects surprise keys. (I did not run these calls; check each provider's current SDK docs.)

:::analogy Shouting an order versus a printed slip
A shouted order gets misheard. A printed checkbox slip is a response guaranteed to match a schema you defined. (Instructor's site.)
:::

### Literal and the retry loop

`Literal` physically limits a classification to allowed values. When validation still fails, the `ValidationError` text (chapter 9) is the trigger for a retry: feed it into the next prompt and ask again, up to a limit.

```python
def classify_with_retry(text, max_retries=3):
    last_error = None
    for _ in range(max_retries):
        raw = ask_llm(text, previous_error=last_error)    # your LLM call
        try:
            return TicketClassification.model_validate_json(raw)
        except ValidationError as e:
            last_error = str(e)
    raise RuntimeError("Failed after max retries")
```

Pydantic AI, built by the Pydantic team, automates this: when validation of an output or a tool's arguments fails, it sends the errors back to the model and asks it to retry. Its docs also show a **validation context**: values your validators read from `info.context` (for example a list of allowed countries) that the model never sees.

### Context-aware validators

A validator can check against data supplied at call time through `model_validate(..., context=...)` (chapter 4), which is how an app can enforce "country must be one of these" without telling the model the list.

:::key Shape, not correctness
Structured output guarantees the **shape**. A well-formed answer can still be confidently wrong. Pydantic's article says the same: structurally valid output does not guarantee correct content, and validation catches type and shape problems, not semantic ones.
:::

### JSON parsing and partial JSON (from the JSON and Experimental pages)

:::note Source
Pydantic docs, [JSON](https://pydantic.dev/docs/validation/latest/concepts/json/), read on 31 Oct 2026 from the docs source on GitHub, which tracks the main branch (text and tables read; long code samples skimmed).
:::

- **Built-in JSON parsing.** `model_validate_json` and `TypeAdapter.validate_json` parse in Rust (the `jiter` parser, v2.5 and later), which is faster than `json.loads` followed by `model_validate`, supports custom errors and honours `strict`. With strict mode on, JSON strings are still accepted for dates and arrays for tuples, because JSON has no such types. A repeated key keeps the last value.
- **Partial JSON, v2.7.** `pydantic_core.from_json(text, allow_partial=True)` returns the parts of an incomplete document that parsed (a cut-off list keeps its finished items; a cut-off object keeps its finished keys). Without the flag an incomplete document is an error. For models, fields should have defaults so a half-received object validates.
- **Partial validation, v2.10 (experimental).** Pass `experimental_allow_partial=True` to `TypeAdapter.validate_json`, `validate_python` or `validate_strings` to validate incomplete input, which suits streamed LLM output you want to show while it arrives. The docs call it a proof of concept with limitations.
- **String caching.** `cache_strings` (default on) caches repeated short strings (under 64 characters, cache of 16,384 entries) to speed parsing and use a little more memory; turn it off when strings rarely repeat.
- **Conversion table.** The docs include a generated table of which input types convert to which field types in lax and strict mode; it is built when the site is built, so its contents were not in the source I read.

## Common mistakes

| Mistake | Symptom | Fix |
| --- | --- | --- |
| Cleaning fences with string code | Breaks when the format shifts | Provider structured output, or a schema-forcing tool call |
| Treating a valid object as true | Wrong facts accepted | Verify facts separately |
| No retry limit | Endless loop and cost | Cap the retries |

## Interview corner

:::qa How do you get reliable JSON from an LLM?
Pass a Pydantic model to the provider's structured-output call (or its JSON Schema as a forced tool), constrain values with `Literal`, validate the result, and retry with the error fed back if it fails.
:::

:::qa Does validation make an answer correct?
No. It confirms the shape and constraints only. A confidently wrong value in the right shape still passes.
:::
