# Settings and secrets
> lead: Replace string-only os.getenv() with a typed settings class that reads the environment and .env files and hides secrets.
meta: Pydantic | Part 6 | 8 min read

## Why it matters

`os.getenv()` always returns a string or `None`. `DEBUG="false"` is a non-empty string, so `if debug:` is true. Every project ends up rewriting the same parsing code.

## Core ideas

`BaseSettings` (from the separate `pydantic-settings` package) extends `BaseModel`. Field names map to uppercase environment variables (`api_key` reads `API_KEY`), `SettingsConfigDict(env_file=".env")` also reads a `.env` file, and every `Field` constraint applies.

```python
from pydantic import Field, SecretStr
from pydantic_settings import BaseSettings, SettingsConfigDict

class AppSettings(BaseSettings):
    model_config = SettingsConfigDict(env_file=".env", extra="ignore")
    api_key: SecretStr
    max_connections: int = Field(default=100, ge=1, le=1000)
    debug: bool = False
```

`settings.max_connections` is an `int`, `debug` is a real `bool`, and `api_key` prints masked; read it on purpose with `.get_secret_value()`.

:::analogy Sensor wires versus a dashboard
`os.getenv()` gives raw unlabeled wires. `BaseSettings` is the dashboard that shows typed gauges.
:::

:::tip Same idea as Foundations chapter 1
The `.env` file that Foundations set up is exactly what this class reads.
:::

## Common mistakes

| Mistake | Symptom | Fix |
| --- | --- | --- |
| `if os.getenv("DEBUG")` | `"false"` is truthy | Use a `bool` field in `BaseSettings` |
| Keys as plain `str` | Secret printed in logs | Use `SecretStr` |

## Interview corner

:::qa Why BaseSettings over os.getenv?
It gives typed, validated configuration with defaults and constraints, reads `.env`, and masks secrets, instead of hand-written string parsing.
:::
