# Nested models
> lead: Use one model as another's field type and validation cascades through every layer, with errors that name the exact path.
meta: Pydantic | Docs "Models", class 03, the notebook | 10 min read

## Why it matters

Real data, including JSON from an API or an LLM, is nested: an applicant has an address, an order has a list of items. The class pointed out that nested models mirror nested JSON, which is the shape of most API payloads and LLM structured outputs.

## Core ideas

```python
from pydantic import BaseModel, Field

class Address(BaseModel):
    city: str
    state: str
    pin_code: str

class Applicant(BaseModel):
    name: str
    email: str
    address: Address
    history: list[str] = []

a = Applicant.model_validate(
    {"name": "R", "email": "r@x.com",
     "address": {"city": "Pune", "state": "MH", "pin_code": "411001"}})
a.address.city          # dot-chain access, fully typed
```

- Validating the outer model builds the inner models from the inner dicts. `model_dump()` converts everything back, recursively.
- A bad inner value gives an error whose location is the full path, such as `address.pin_code`.
- A whole nested object can be optional with `Address | None = None`. Lists of models work the same way. There is no practical depth limit.
- The notebook's version of this puts a `Field(gt=1000, lt=43125315)` constraint on `pin_code`, to show that nested models carry their own rules.

:::analogy The org chart
A company contains departments, which contain employees. Validate the company and every layer beneath is validated for you. (Instructor's site.)
:::

### Inheritance is also allowed

From the class Q&A: a model can extend another (`class Applicant(Address)` inherits its fields and validators) with ordinary Python inheritance. Prefer composition (a field of type `Address`) when the data really is "has an", and inheritance only when it is "is a".

### Self-referencing data and forward references

Data that refers to itself (a parent that points back to a child) is detected and reported as a `ValidationError` instead of recursing forever. A model that mentions a class defined later uses a string annotation, and you call `model_rebuild()` once the names exist.

### Unions (from the official Unions page)

:::note Source
Pydantic docs, [Unions](https://pydantic.dev/docs/validation/latest/concepts/unions/), read in full on 31 Oct 2026.
:::

A union is different from every other type: only **one** member has to validate. Three approaches exist.

- **Left to right** (`Field(union_mode='left_to_right')`): members are tried in order, the first success wins. Order matters: with `id: int | str`, the string `'456'` becomes the integer `456`, because lax mode lets it pass `int` first. If all members fail, you get one error per member.
- **Smart mode** (the default in V2). It tries all members and picks the best match using two scores: the **number of valid fields set** (for models, dataclasses and `TypedDict`, added in v2.8.0; nested fields count too) and then **exactness** (exact type match, then success in strict mode, then success in lax mode). The algorithm may change in minor releases, so use left to right or a discriminator if you rely on exact behaviour.
- **Discriminated (tagged) unions:** only one member is tried, chosen by a tag, so validation is faster and errors are shorter. Use `Field(discriminator='pet_type')` on a union of models that each have a `Literal` field, or the `Discriminator` class with `Tag` for a **callable** discriminator (it must handle both dicts and model instances, and returning `None` gives a `union_tag_not_found` error). Only one discriminator per field is allowed, so nest `Annotated` unions for two levels. The generated JSON Schema carries the OpenAPI `discriminator`.
- **Errors.** Plain unions give verbose errors, especially for recursive models. `Discriminator` accepts `custom_error_type`, `custom_error_message` and `custom_error_context`, and `Tag` names make error locations readable.
- Not captured: the "all other types" tab of the smart-mode steps, so only the model steps are confirmed.

### Dataclasses and TypeAdapter (from two official pages)

:::note Sources
Pydantic docs, [Dataclasses](https://pydantic.dev/docs/validation/latest/concepts/dataclasses/) and [Type Adapter](https://pydantic.dev/docs/validation/latest/concepts/type_adapter/), both read in full on 31 Oct 2026.
:::

**Pydantic dataclasses.** `@pydantic.dataclasses.dataclass` adds validation to a standard dataclass, so `User(id='42', signup_ts='2032-06-21T12:00')` converts the values. The docs say they are **not a replacement** for models.

- Same as models: configuration (but no `model_config` attribute), nested classes, and `Field()` or `dataclasses.field()`.
- Different: no `model_validate`, `model_dump` or JSON Schema methods (wrap the class in `TypeAdapter`); extra data is dropped from serialization; generics are supported but a parameterised class like `Foo[int]` is treated as `Foo[Any]`, so wrap it in `TypeAdapter`.
- Config: the `config=` argument or a `__pydantic_config__` attribute. `rebuild_dataclass()` rebuilds the schema.
- Stdlib dataclasses can be inherited, and used as fields in a model; for Pydantic to **revalidate** an existing instance the model needs `revalidate_instances='always'`. Arbitrary types need `arbitrary_types_allowed`. `is_pydantic_dataclass()` tells the two kinds apart.
- Validators work. `__post_init__` runs between the before and after model validators, and in a before validator the input is an `ArgsKwargs` object, not a dict.

**TypeAdapter** validates, serializes and builds JSON Schema for any type without a model. `TypeAdapter(list[User])` validates a list of `TypedDict`s, and `validate_python`, `dump_python`, `dump_json` and `json_schema` are the main methods.

- `dump_json` returns **bytes**, while `model_dump_json` returns a `str` (a V1 compatibility leftover).
- Do not use `TypeAdapter` as a field type.
- Building it has noticeable cost, so **create it once and reuse it**.
- `defer_build=True` (v2.10) postpones the build; `rebuild()` builds it later, which helps with forward references.
- Not captured: the Python 3.12 tab of the generic dataclass example.

### Forward annotations and cyclic imports (from the Forward Annotations page)

:::note Source
Pydantic docs, [Forward Annotations](https://pydantic.dev/docs/validation/latest/concepts/forward_annotations/), read on 31 Oct 2026 from the docs source on GitHub, which tracks the main branch (text and tables read; long code samples skimmed).
:::

- **Python 3.14 and later** no longer evaluates annotations eagerly, so you can refer to names defined later without quotes.
- **Python 3.13 and earlier:** quote the annotation (`'MyInt'`) or add `from __future__ import annotations`. Self-referencing models need a quoted name, for example `sibling: 'Foo | None' = None`, because the class is not defined while its own body runs.
- **Cyclic imports** (two models in two modules referring to each other): import one only under `if TYPE_CHECKING:` and quote the annotation; Python 3.15 adds `lazy` imports.
- Pydantic resolves these names when the model is created, or later with `model_rebuild()`.

### Unions: what changed from V1

In V1 a union tried members left to right and returned the first that validated. V2 keeps the input's type when it already matches a member: with `float | int`, the `int` 1 stays an `int`. Annotate with `Field(union_mode='left_to_right')` to get the V1 behaviour back.

## Common mistakes

| Mistake | Symptom | Fix |
| --- | --- | --- |
| Expecting int to str coercion in a nested field | A nested `12345` is rejected for a `str` field | Convert it yourself |
| Calling `dict()` and expecting nested dicts | Inner models stay as models | Use `model_dump()` |
