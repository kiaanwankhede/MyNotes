# Computed fields and serialization
> lead: Derive values instead of storing stale ones, then control exactly what leaves a model: dict or JSON, which fields, which names, and in what shape.
meta: Pydantic | Docs "Serialization" and "Fields", the notebook | 15 min read

## Why it matters

Some values should always be calculated from others, and almost every real API must hide or trim fields. Both are small settings once you know them.

## Core ideas

### @computed_field

Stack `@computed_field` on a `@property`. The value is read-only, appears in `model_dump()` and in the serialization JSON schema (marked read-only), and is recomputed on every access. Pydantic adds no validation or caching to the property.

```python
from pydantic import BaseModel, computed_field

class JobApplication(BaseModel):
    full_name: str
    years_experience: int

    @computed_field
    @property
    def experience_tier(self) -> str:
        return "junior" if self.years_experience < 2 else "mid" if self.years_experience < 7 else "senior"
```

### dict, JSON and modes

| Call | Result |
| --- | --- |
| `model_dump()` | A Python dict; nested models converted recursively. Values keep Python types (a tuple stays a tuple) |
| `model_dump(mode="json")` | Only JSON-compatible types (a tuple becomes a list). The notebook uses this to write `account.json` |
| `model_dump_json()` | A JSON string, with support for datetimes, UUIDs and sets |

### Choosing fields

| Option | Effect |
| --- | --- |
| `include`, `exclude` | Sets, or nested dicts to reach into lists (`'__all__'` for every item) |
| `Field(exclude=True)` | Always omit this field; wins over `include` |
| `exclude_none=True` | Drop fields currently `None` |
| `exclude_defaults=True` | Drop fields equal to their default |
| `exclude_unset=True` | Keep only fields the caller explicitly set; the one for PATCH-style partial updates. Assigning a field later adds it to the set |
| `by_alias=True` | Use `serialization_alias` names |

### Custom serializers

`@field_serializer` changes how one field is written (for example a datetime to an epoch number), and `@model_serializer` shapes the whole output. **Plain** mode replaces Pydantic's logic; **wrap** mode calls a handler and edits the result. Only one serializer applies per field or model.

### Subclasses and secrets

When a field is annotated with a model type, only that type's declared fields are serialized, even if the value is a subclass. This is deliberate: it stops a subclass's extra field (such as a password) leaking by accident. Opt in to the runtime subclass with `polymorphic_serialization` or `serialize_as_any`.

## Common mistakes

| Mistake | Symptom | Fix |
| --- | --- | --- |
| Storing a derived value | It drifts out of sync | `computed_field` |
| PATCH that dumps defaults | Overwrites stored data with defaults | `exclude_unset=True` |
| Writing `model_dump()` straight to a JSON file | A non-JSON type raises | Use `mode="json"` or `model_dump_json()` |

## Interview corner

:::qa Why exclude_unset for PATCH?
It serialises only what the caller explicitly provided, so unset defaults do not overwrite stored values.
:::

:::qa model_dump versus model_dump(mode="json")?
The first keeps Python types; the second converts to JSON-compatible ones (tuples to lists, and so on).
:::
