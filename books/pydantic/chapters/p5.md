# Nested models
> lead: Use one model as another's field type and validation cascades through every layer, with errors that name the exact path.
meta: Pydantic | Part 5 | 8 min read

## Why it matters

Real data (JSON from an API or an LLM) is nested: an applicant has an address, an order has a list of items.

## Core ideas

```python
from pydantic import BaseModel

class Address(BaseModel):
    city: str
    pin_code: str

class Applicant(BaseModel):
    name: str
    address: Address
    history: list[str] = []

a = Applicant.model_validate({"name": "R", "address": {"city": "Pune", "pin_code": "411001"}})
a.address.city          # dot-chain access, typed
```

A bad inner value raises an error that points at `address.pin_code`, however deep. A whole nested object can be optional with `Address | None = None`. There is no practical depth limit, and lists of models work the same way.

:::analogy The org chart
A company contains departments, which contain employees. Validate the company and every layer beneath is validated for you.
:::

:::trap Coercion is not symmetric here either
A nested `12345` will not become the string `"12345"`. It is rejected; convert it yourself if you need to.
:::

## Common mistakes

| Mistake | Symptom | Fix |
| --- | --- | --- |
| Passing a model instance where a dict is expected, or the reverse | Confusing errors | `model_validate` accepts a dict; instances pass as they are |

## Interview corner

:::qa How does validation work for nested data?
Pydantic builds the inner model from the inner dict and validates it with its own rules; errors report the full path, such as `address.pin_code`.
:::
