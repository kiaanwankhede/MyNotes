# Why validation exists, and type hints
> lead: Python will happily run with garbage data. Type hints say what you expect, but only a library like Pydantic enforces it at the door.
meta: Pydantic | Class 03, the notebook, the instructor's site | 10 min read

## Why it matters

Data from outside your code (an API, a form, a file, an LLM) can be anything. If nothing checks it when it arrives, the crash happens deep inside, far from the real cause. Pydantic's own docs describe it as the most widely used validation library for Python, and the class note lists the Anthropic and OpenAI SDKs among the places it is used.

## Core ideas

### Why Python is "loose"

The class explained it like this: in Java or C++ a variable reserves a block of memory of a declared type. In Python a variable is a pointer to a value, so the same name can point at an int, then a string, then a list, with no complaint. That is great for learning and dangerous in production, where real users, or people trying to break the system, send you data.

:::analogy The courier with no intake desk
A courier that loads any parcel finds the problem three stops into the route. Pydantic is the intake desk that refuses a bad parcel at the door. (From the instructor's site.)
:::

The notebook shows it with `register_user`: it computes `2026 - age`. `age=28` works. `age="unknown"` crashes inside the subtraction, and `age=10000` quietly gives a birth year of -7974, because the types are fine and the **value** is nonsense. That is the difference between **type validation** (what kind of data) and **data validation** (does the value make sense).

:::tip The class's point on AI-written code
If AI writes your code, you still need to understand Pydantic to debug or trust it. (Class 03, paraphrased.)
:::

### Type hints are documentation, not enforcement

`age: int = "not a number"` runs. Hints are read by humans, IDEs and Pydantic, and nothing else at runtime.

```python
tags: list[str] = ["python", "pydantic"]     # lowercase built-ins since Python 3.9
word_counts: dict[str, int] = {"error": 12}

def format_price(amount: float, currency: str = "USD") -> str:
    return f"{currency} {amount:.2f}"
```

### Optional and Literal

`str | None` (or `Optional[str]`) allows a missing value. The class adds a Python reminder: the missing value is `None`, with a capital N; there is no `null`. `Literal["low", "medium", "high"]` limits a value to a fixed set. Alone they are only documentation; with Pydantic they are enforced, and `Literal` is how you stop a model returning "kinda urgent i guess".

## Common mistakes

| Mistake | Symptom | Fix |
| --- | --- | --- |
| Believing a hint is a check | Wrong types flow through silently | Validate at the boundary with a `BaseModel` |
| Checking only the type | `age=10000` passes | Add value constraints (chapter 3) |

## Interview corner

:::qa Does Python enforce type hints?
No. At runtime they are ignored. They help readers, IDEs and libraries such as Pydantic, which reads them and enforces them.
:::

:::qa What is the difference between type validation and data validation?
Type validation checks the kind of data (an int). Data validation checks the value makes sense (an age of 10000 is an int but not valid). Pydantic does both: types from hints, values from `Field` constraints and validators.
:::
