# Your first model
> lead: A BaseModel validates on creation, converts safe values, collects every error, and has a small set of methods you should know by name.
meta: Pydantic | Docs "Models", class 03, the notebook | 15 min read

## Why it matters

A plain class and a dataclass look like a model but check nothing. Only `BaseModel` refuses bad data before the object exists.

## Core ideas

### Three ways to define a data shape

| Option | Accepts arguments | Validates |
| --- | --- | --- |
| Plain class (you write `__init__`) | Yes | No |
| `@dataclass` (auto `__init__`) | Yes | No: `age="banana"` is accepted |
| `BaseModel` | Yes | Yes |

The class demo showed a plain class and a dataclass silently accepting garbage, and only `BaseModel` raising at once.

:::analogy The customs form
A plain class is a form nobody hands out, a dataclass is a form nobody reads, and a `BaseModel` is a form with an officer behind it. (Instructor's site.)
:::

```python
from pydantic import BaseModel, ValidationError

class SignupForm(BaseModel):
    username: str
    age: int
    newsletter_opt_in: bool = False     # a default makes it optional

SignupForm(username="a", age="28", newsletter_opt_in="True")   # age -> 28, flag -> True
try:
    SignupForm(username="Mayank")        # missing age
except ValidationError as e:
    print(e)                             # lists every problem field
```

A default value is what makes a field optional; without one the field is required. If you do not know the right default, use `None`.

### Coercion ("lax mode")

Pydantic converts reasonable input: the string `"28"` becomes `28`. It refuses what it cannot convert safely: `"28eight"` fails, and so does `28.5` for an `int` field (class demo). The docs add that conversion can lose information in some cases (a float like `3.0` becomes `3`) and that **strict mode** turns conversion off (chapter 7).

:::trap Coercion is not symmetric
`"25"` becomes `25` for an `int` field, but `12345` is **not** turned into `"12345"` for a `str` field. It is rejected. (Instructor's site.)
:::

### The methods to know

| Method | Use |
| --- | --- |
| `Model(**data)` / `Model.model_validate(data)` | Validate a dict (the second takes options such as `strict=True`) |
| `Model.model_validate_json(text)` | Validate a JSON string or bytes directly; generally faster than parsing the JSON yourself |
| `model_dump()` / `model_dump_json()` | Back to a dict or JSON string (chapter 5) |
| `model_json_schema()` | The JSON Schema for the model (chapter 7) |
| `model_copy(update=...)` | Copy; the updates are **not** validated, and the copy is shallow unless `deep=True` |
| `model_construct()` | Build **without validation**, for data you already trust; nested dicts stay dicts and the result can be invalid |
| `model_fields_set` | Which fields were explicitly provided |

The docs use "validate" for everything except JSON, where they say "parse". The model's guarantee is about the **output**: after validation the object matches its declared types and constraints.

### Extra data

By default unknown keys are silently **ignored**. `extra="forbid"` raises an error, and `extra="allow"` keeps them. Add `extra="forbid"` to any model you hand to an LLM provider as a schema, so the model cannot add surprise keys.

### Other behaviours worth knowing

- Models are mutable by default; `frozen=True` blocks assignment (a "faux" immutability, since nested dicts can still change).
- Fields are validated in declaration order, and errors, serialization and schema follow that order.
- Names starting with an underscore are private attributes, not fields.
- `from_attributes=True` lets a model read attributes from any object, which is how ORM objects are validated.
- Inheritance works: a model can extend another and inherit its fields and validators (class Q&A).
- A custom `__init__` is discouraged; use an after-validator or `model_post_init` instead.

### Configuration in depth (from the official Configuration page)

:::note Source
Pydantic docs, [Configuration](https://pydantic.dev/docs/validation/latest/concepts/config/), read in full on 31 Oct 2026.
:::

Behaviour is controlled by `ConfigDict` values. Where you can set them:

- **Models:** `model_config = ConfigDict(...)` (a plain dict also works) or class arguments such as `class Model(BaseModel, frozen=True)`. Type checkers understand class arguments, so `frozen=True` makes mutation a type error. The old V1 `Config` class still works but is deprecated.
- **Pydantic dataclasses:** `@dataclass(config=ConfigDict(...))`.
- **`TypeAdapter`:** `TypeAdapter(list[str], config=ConfigDict(coerce_numbers_to_str=True))`. Passing config when the adapter wraps a type that already has its own config is a usage error.
- **Stdlib dataclasses and `TypedDict`:** a `__pydantic_config__` attribute, or the `@with_config` decorator (which avoids type-checking errors on `TypedDict`).
- **`@validate_call`** also accepts config.
- **Inheritance.** Subclass config is merged with the parent's, so one custom parent class can change behaviour globally. With several base classes Pydantic does not currently follow the method resolution order (the docs link an open issue).
- **`plugin_settings`** passes options to plugins, keyed by plugin name; the main one is Logfire, for example `{'logfire': {'record': 'failure'}}` to record only failures.
- **Propagation, the surprise.** Pydantic models and Pydantic dataclasses are each a **configuration boundary**: a parent's `str_to_lower=True` does not reach a nested `User` model. Stdlib dataclasses and `TypedDict` **do** inherit the parent's config unless they set their own.

### Coming from Pydantic V1 (from the Migration Guide)

:::note Source
Pydantic docs, [Migration Guide (V1 to V2)](https://pydantic.dev/docs/validation/latest/get-started/migration/), read on 31 Oct 2026 from the docs source on GitHub, which tracks the main branch (text and tables read; long code samples skimmed).
:::

- **Method renames.** Every non-deprecated `BaseModel` method is now `model_*` or `__pydantic_*__`: `dict()` is `model_dump()`, `json()` is `model_dump_json()`, `parse_obj()` is `model_validate()`, `copy()` is `model_copy()`, `construct()` is `model_construct()`, `update_forward_refs()` is `model_rebuild()`, `__fields__` is `model_fields`. The old names still work but emit a `DeprecationWarning`. `parse_raw` and `parse_file` are deprecated: use `model_validate_json`, or load the data and call `model_validate`. `from_orm` is replaced by `model_validate` with `from_attributes=True`.
- **Equality is stricter.** A model equals only another model of the same type with the same field values, extra values and private attribute values; it no longer equals a dict.
- **`__root__` became `RootModel`.** `RootModel` does not support `arbitrary_types_allowed`.
- **Required versus optional matches dataclasses.** `f: Optional[str]` is **required but may be `None`**; `f: Optional[str] = None` is optional. A field annotated `Any` no longer defaults to `None`.
- **Floats to integers.** V1 accepted any float for an `int` field and lost the decimals; V2 accepts a float only when its decimal part is zero.
- **Input types are not preserved.** V1 tried to keep, say, a `Counter` passed for a `Mapping[str, int]`; V2 does not, for speed and consistency.
- **Numbers are not coerced to strings** by default (turn on `coerce_numbers_to_str`).
- **Tools.** `bump-pydantic` (beta) rewrites V1 code; the V1 API remains importable as `pydantic.v1`. `BaseSettings` moved to `pydantic-settings`, `Color` and payment-card types to `pydantic-extra-types`.

## Common mistakes

| Mistake | Symptom | Fix |
| --- | --- | --- |
| Using a dataclass for external data | Bad types pass silently | Use `BaseModel` |
| Trusting `model_construct()` output | Invalid data inside a "model" | Use it only for already-validated data |
| Assuming unknown keys raise | They are dropped silently | Set `extra="forbid"` |

## Interview corner

:::qa BaseModel versus dataclass?
Both give a clean constructor from hints. Only `BaseModel` validates and coerces, raising one `ValidationError` before the object is created.
:::

:::qa What does the default extra setting do?
It ignores unknown keys. `forbid` raises; `allow` stores them.
:::

:::qa model_validate versus model_construct?
`model_validate` checks the data. `model_construct` skips all checks, so use it only for data you already trust.
:::
