## Why it matters

This is where Pydantic is "everywhere": an endpoint that takes a model is validated before your function body runs.

## Core ideas

```python
from fastapi import FastAPI
from pydantic import BaseModel, EmailStr, Field

app = FastAPI()

class Applicant(BaseModel):
    full_name: str = Field(min_length=2, max_length=100)
    email: EmailStr

class Receipt(BaseModel):
    full_name: str

@app.post("/apply", response_model=Receipt)
def apply(a: Applicant) -> Receipt:
    return Receipt(full_name=a.full_name)
```

- **Request validation.** Malformed bodies are rejected with a detailed error before the function runs; no manual `if` checks.
- **`response_model=`** filters what you return down to that shape, a safety net against leaking extra fields.
- **Docs.** The model's JSON Schema feeds the `/docs` page, so every `Field()` constraint becomes a documented API constraint.

:::analogy One scanner at the terminal entrance
Instead of each gate building its own detector, the terminal has one scanner everyone passes. Your model is that scanner. (Instructor's site.)
:::

## Common mistakes

| Mistake | Symptom | Fix |
| --- | --- | --- |
| Returning an internal model directly | Password or internal ids leak | Declare `response_model` |

## Interview corner

:::qa What does response_model do?
It validates and filters the returned object to the declared shape, so extra fields cannot leak, and it documents the response in `/docs`.
:::
