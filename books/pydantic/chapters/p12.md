## The ecosystem map

This book covers core Pydantic: models, fields, validators, computed fields, serialization, strict mode, JSON Schema, settings, errors, and structured output with provider SDKs. The docs list much more, which this book does not teach: unions and discriminators in depth, `TypeAdapter`, dataclasses, generics, `RootModel`, performance, the architecture notes, and extra-types packages.

- **One layer up:** Instructor patches an LLM client to validate and retry automatically, which is the retry loop from chapter 11 wrapped up.
- **Two layers up:** agent frameworks use Pydantic for tool schemas and structured outputs and add orchestration. **Pydantic AI** is made by the Pydantic team; LangChain and CrewAI also build on Pydantic. Orchestration (when to call a tool, state across turns) is not Pydantic's job; validating data against a schema is.
- The docs say around 8,000 PyPI packages use Pydantic, with FastAPI, SQLModel and LangChain among them.

:::beyond Out of scope here
LangChain is taught in the next book. This book does not teach Instructor, Pydantic AI or CrewAI.
:::

## Final project: support-ticket triage

`POST /triage` takes a messy support message and returns a validated result: category, priority, sentiment, a computed SLA and redacted customer info.

| Piece | Concept used |
| --- | --- |
| `IncomingTicket` | A `mode="before"` `field_validator` redacts email addresses before storing (chapter 4), and it is the FastAPI request body (chapter 10) |
| `TriagedTicket` | `Literal` for category, priority and sentiment (chapter 11); a nested `CustomerInfo` (chapter 6); `extra="forbid"` (chapter 2) |
| `sla_hours` | A `computed_field` from priority: high 4, medium 24, low 72 (chapter 5), so the LLM never does arithmetic |
| Safety net | A `model_validator` rejects `high` priority with `general_question` (chapter 4) |
| `AppSettings` | Picks Anthropic, then OpenAI, then a free OpenRouter model, whichever key exists (chapter 8) |

## Common mistakes

| Mistake | Symptom | Fix |
| --- | --- | --- |
| Letting the LLM compute derived values | Inconsistent numbers | Derive them with `computed_field` |
| Assuming a framework replaces understanding | Cannot debug failures | Know the validate-and-retry loop first |

## Interview corner

:::qa How would you design a reliable LLM-backed API endpoint?
Validate and clean the request with a model, ask the provider for a structured response in a `Literal`-constrained schema, derive computed values in code, add a model validator for impossible combinations, and cap retries.
:::
