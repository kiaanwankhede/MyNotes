# Retrieval and the answer chain
> lead: Three retrieval strategies with one signature, wrapped into a sixteen-line chain that answers only from the retrieved text.
meta: RAG | Meridian slides and code | 15 min read

## Why it matters

Retrieval is where answers are won or lost. Seeing retrieval as "question in, documents out" makes every variant in the next chapter easy to add.

## Core ideas

**Retrieval:** three strategies, chosen by a parameter:

| Strategy | What it does |
| --- | --- |
| `similarity` (default) | The **3** chunks closest in meaning to the question. Fast |
| `multiquery` | Gemini **rewrites the question several ways** and merges the results |
| `contextual` | Fetch **10** chunks, then Gemini **trims each** to the relevant part |

```python
rag_chain = create_retrieval_chain(build_retriever(retriever_type), question_answer_chain)
```

The system prompt says: use the retrieved context, and **if you do not know based on the context, say so**. That is the guard against making things up. Try it: ask something not in the documents and the answer should say it does not know.

```python
def build_rag_chain(retriever_type: str = "similarity"):
    """question (str) -> answer (str), written as one LCEL pipeline."""
    return (
        {"context": build_retriever(retriever_type) | format_docs, "input": RunnablePassthrough()}
        | ANSWER_PROMPT
        | get_llm()
        | StrOutputParser()
    )
```

Each strategy is a plain function from a question to a list of documents:

| Choice in the screen | `retriever_type` | What it does | Trade-off |
| --- | --- | --- | --- |
| Normal | `similarity` | The 3 closest chunks (`k=3`) | Fastest |
| Multi-Query | `multiquery` | The model writes 3 alternative phrasings with **structured output**, searches with all 4, and merges while dropping duplicates | Finds more, slower |
| Contextual Compression | `contextual` | Fetches 10 chunks, then the model copies only the relevant sentences from each (or replies `NO_OUTPUT`, which drops the chunk) | Cleanest, slowest |

The legacy helpers moved to `langchain-classic` in LangChain v1, so the two advanced strategies are written out in a few lines each, which is also easier to explain in an interview.

:::beyond Retriever search types in LangChain
Any vector store becomes a retriever with `.as_retriever()`, which accepts a `search_type`: `"similarity"` (closest by meaning), `"mmr"` (maximal marginal relevance: relevant **and** diverse, so you do not get three near-duplicate chunks) or `"similarity_score_threshold"` (only chunks above a relevance score), plus `search_kwargs` such as `k`. Because every vector store implements the same interface, swapping the database is a one-line change. Source: the course's LangChain interview question PDF.
:::

:::repo The retrieval code imports from `langchain_classic`
`retrieval.py` imports chains and retrievers from `langchain_classic` (the legacy package from Chapter 2) while the agents use the current `create_agent`. The project mixes old and new, which is realistic. Know which parts are Classic when you read it.
:::

### The chain, step by step

three strategies with one signature (question in, documents out) chosen from a dictionary, wrapped in `RunnableLambda`, then the whole chain in sixteen lines. Contextual compression runs `batch` over the chunks in parallel. Similarity is one model call, multi-query two, contextual one plus one per chunk.

### The lab: ask the four documents

write the expected answers first, because a test without an expected answer is just a demo (EUR 2.84 billion, Net-45, 2.2 percent, 10 years, an honest refusal). All five matched in about 24 seconds. Ask the log, not memory: each question leaves a `RAG query received` line.

## From the Meridian slides in full: chapters 19 and 20

**Chapter 19, `retrieval.py` (115 lines).** Retrieval has four jobs: find the closest chunks (three strategies with one signature, question in and documents out), format them as one block with source names, instruct the model to answer only from that text, and answer. The system prompt is a job description whose second sentence is the honest exit. A second prompt, used only by contextual compression, returns the marker `NO_OUTPUT` for "nothing relevant". The plain search is one line: ask the store for the `k=3` closest chunks. Multi-query uses `with_structured_output` so Gemini returns an `AlternativeQuestions` shape (one model call, three rewrites), searches the original plus the three, and merges while skipping duplicates (up to four chunks). Contextual compression fetches ten chunks, builds a tiny chain (extraction prompt, model, text), runs `batch` over the chunks in parallel and drops empty answers and `NO_OUTPUT`; in the run one 193-character chunk survived. A dictionary of functions picks the strategy from the API's `retriever_type`, falling back to similarity with a warning; `RunnableLambda` wraps a plain function so it can join the pipe; `format_docs` joins the chunks with their source names. The chain, in sixteen lines: question in, context retrieved and formatted while the question passes through, both fill the answer prompt, the shared Gemini model, a string parser; read the pipe as "and then". This is LCEL.

| Mode | Model calls | In the prompt | One run |
| --- | --- | --- | --- |
| Similarity | 1 (the answer) | 3 chunks | 7.1 s |
| Multi-query | 2 (rewrite, answer) | up to 4 chunks, merged | 12.0 s |
| Contextual | 1 plus one per chunk fetched | only the relevant sentences | 9.7 s |

All three answered Net-45 correctly; the differences are cost and prompt size. Start with similarity, move to multi-query for vague questions or documents that use other words, and to contextual when chunks are long and noisy.

**Chapter 20, the lab.** A test without an expected answer is just a demo, so the answers are written first: revenue FY2024 about EUR 2.84 billion; servo-motor payment terms Net-45; customs duty on programmable controllers from Japan 2.2 percent; filling-line equipment depreciated over 10 years straight line; and a deliberate fifth question, "who won the football World Cup in 2022?", whose right answer is an honest refusal. All five matched in about 24 seconds (the refusal's wording varies, the refusal does not). Every question leaves two log lines, `RAG query received` (question and mode) and `RAG answer generated` (the text), which is how you answer "what did the system say at 2 a.m.?". If something goes wrong: a wrong fact (check the log, then the chunks found, then try multi-query); "I don't know" for a covered question (the index may be empty: ingest again and expect four, four, four); a 503 or API error (the key or a retired model name, set `VERTEX_LLM_MODEL_NAME`); a real answer to the football question (the instruction line is missing from the prompt); slow answers (network, or a mode with extra calls).
