# Embeddings, storing meaning and ingestion
> lead: How text becomes numbers, where those numbers are kept, and how a PDF is cut into chunks so the same file can be re-indexed without duplicates.
meta: RAG | Meridian slides and code | 15 min read

## Why it matters

Ingestion decisions (chunk size, overlap, which embedding model) decide what retrieval can ever find. If they are wrong, no clever retriever can repair it.

## Core ideas

### Talking to Gemini and turning text into numbers

one shared model connection, created on first use with `lru_cache`. `extract_text` joins Gemini's content blocks because a reply may be a **list of blocks**. Real closeness scores sit in a narrow band (0.85 for the right sentence against 0.55 and 0.57 for the others), so unrelated is not zero. Numbers from two embedding models are like temperatures in two unknown units: they cannot be compared.

### Storing meaning, and keeping the originals

a vector store keeps numbers, text and source, and survives a restart because Chroma writes to a folder. **Keep the originals**: a new embedding model, chunk size or bug fix means re-indexing everything. `basename` keeps only the file name so an uploaded name cannot write outside the folder.

### Ingestion

three reasons to cut (a document is too big, one vector for a page describes everything and nothing, and a sentence can be lost). Chunk ids are a `sha1` of source, page and position, so **indexing the same file twice replaces rather than duplicates** (the count stays at one).

### Ingestion in the Meridian code

**Ingestion:** PDF, then pages, then chunks of about 1,000 characters, then embeddings, then Vector Search. Neighbouring chunks share **100 characters** (`CHUNK_OVERLAP = 100`) so sentences are not cut off. Each chunk keeps its `source` in metadata so an answer can be traced to a file.

```python
splitter = RecursiveCharacterTextSplitter(chunk_size=CHUNK_SIZE, chunk_overlap=CHUNK_OVERLAP)
```

Embedding settings come from configuration: the embedding model must output **768 dimensions** to match the Vector Search index. A mismatch is a classic deployment bug.

### Local and cloud stores

The app has one switch, `APP_MODE`, that decides which vector database sits behind ingestion and retrieval.

| Concern | Local | Cloud |
| --- | --- | --- |
| Embeddings | `gemini-embedding-001` (API key) | `text-embedding-005` (Vertex AI) |
| Vector database | Chroma in `.meridian/chroma` | Vertex AI Vector Search |
| Original PDFs | `.meridian/uploads/` | A Cloud Storage bucket |

Everything that needs storage asks one question (`settings.is_cloud`) and receives a LangChain `VectorStore`, so ingestion and retrieval never know which database is behind them. This is the **strategy pattern**: same interface, swappable implementation. Both modes use 768-dimensional vectors, but the two databases are separate, so re-upload after switching. The deployment side of `APP_MODE` is in the last chapter of the LangChain book.

## From the Meridian slides in full: chapters 16 to 18

**Chapter 16, the model and the embeddings (`rag/llm.py` 35 lines, `rag/embeddings.py` 41).** Two jobs need the model (answering and later the audit agents), so one shared connection avoids two configurations. `get_llm()` is created on first use, not on import, so the API can start and answer health checks before any key exists, and `lru_cache` keeps one object. An empty key raises `ConfigurationError` with the address to get a key (HTTP 503 in the API). Gemini may reply with a list of content blocks, so `extract_text` keeps every text block and joins them; a plain string passes through. A gotcha found while writing the variants lab: `reply.text` is a special string type that the Google embedding client rejected (a 500 INTERNAL), while `extract_text(reply.content)` returns a plain string and works. `embeddings.py` follows `APP_MODE`: local uses `gemini-embedding-001` through the Gemini API with a key; cloud uses `text-embedding-005` through Vertex AI with Google Cloud credentials; both give 768 numbers, through one class (`GoogleGenerativeAIEmbeddings`, with `vertexai=True` for the cloud). `embed_query` turns one question into numbers; `embed_documents` does several at once, which is what indexing uses. Numbers from two models are like temperatures in two unknown units, and a store built for 768 numbers refuses 3,072. Change the model and you must re-index everything and keep one index per model; local and cloud both give 768 numbers but are different models, so never point cloud queries at a local index.

**Chapter 17, storing meaning (`vector_store.py` 54 lines, `document_store.py` 80).** The vector store keeps each chunk's numbers, text and source, finds nearest chunks, and survives a restart because Chroma writes to a folder (`.meridian/chroma`). The rest of the code uses only `add_documents`, `similarity_search` and `as_retriever`. The Chroma import sits inside the function so cloud images do not load it; the cloud path checks the settings with the Module 3 helper, raises an error naming any empty ones, imports Google Cloud packages only then, and builds the store from project, region, index and endpoint (`stream_update` makes new chunks searchable quickly). `get_vector_store()` connects on first use and one expression chooses the store from `APP_MODE`. The vector database holds chunks, not PDFs, so a new embedding model, chunk size or bug fix means re-indexing from the **originals**; `document_store` has `save` (a folder locally, a bucket in the cloud) and `pdfs`, a context manager that downloads to a temporary folder in the cloud and yields a path and a source name (`local://file.pdf` or `gs://bucket/file.pdf`) that is saved in every chunk. `basename` keeps only the file name so an uploaded name cannot point outside the folder.

**Chapter 18, ingestion (`data_ingestion.py`, 73 lines).** Three reasons to cut: a whole document is too big and costs more the longer it is, one set of numbers for a whole page describes everything and nothing, and a sentence is often the answer. The four sample PDFs are 645, 664, 845 and 950 characters, so each is exactly one chunk; the chunking matters for your own longer documents. `PyPDFLoader` reads page by page; the splitter uses 1,000 and 100; `split_documents` keeps each page's metadata. Chunk ids are a `sha1` of source, page and position, so the same chunk always gets the same id and indexing again replaces instead of duplicating (the lab shows the count staying at one; random ids would give two and duplicate answers). `ingest_pdf` reads, turns a bad PDF into an `IngestionError` (HTTP 422), stamps the source on every page, cuts, assigns ids, embeds and stores. `ingest_stored_pdfs` logs where it is indexing, opens every stored PDF, calls `ingest_pdf` for each and counts files, pages and chunks (four, four, four); an empty store is a warning, not an error. The upload endpoint uses `ingest_pdf` and the "index everything" button uses `ingest_stored_pdfs`. Only text PDFs work: a scan has no text until OCR is applied.

## From the docs: a semantic search engine in LangChain primitives

*From the LangChain tutorial [Build a semantic search engine](https://docs.langchain.com/oss/python/langchain/knowledge-base), read in full on 31 Oct 2026. It is the generic version of what Meridian does.*

1. **Document.** LangChain's unit of text: `page_content`, a `metadata` dict (source, relations) and an optional `id`. A document is often one chunk of a bigger file.
2. **Embeddings.** Vector search stores numeric vectors and compares a query vector of the **same dimension** by cosine or similar. The page lists many providers (OpenAI, Azure, Google Gemini, Vertex, Bedrock, HuggingFace, Ollama, Cohere, Mistral and others) behind one interface, and a deterministic fake for tests.
3. **Vector store.** Add and query `Document`s with similarity metrics. Choices span in-memory (`InMemoryVectorStore`), hosted and self-run stores (Chroma, Pinecone, Qdrant, Milvus, PGVector, MongoDB and others), all behind the same methods.
4. **Load and split a PDF.** A page is often too coarse, so split it. `RecursiveCharacterTextSplitter` splits recursively on common separators until chunks reach the target size and is the recommended splitter for generic text; the page uses `chunk_size=1000, chunk_overlap=200, add_start_index=True` (which keeps each chunk's character offset in `start_index`). A 107-page filing became 516 chunks.
5. **Index and query.** `add_documents` indexes the chunks. Query by string (`similarity_search`), async (`asimilarity_search`), with scores (`similarity_search_with_score`; here the score is a distance, so lower means closer, and meaning varies by provider) or by vector (`similarity_search_by_vector`). Search by similarity or by maximal marginal relevance.
6. **Retrievers.** A vector store is not a Runnable; a **retriever** is, so it supports `invoke` and `batch` sync and async. Wrap a function with `@chain`, or use `vector_store.as_retriever(search_type=..., search_kwargs={"k": 1})`. Search types: `"similarity"` (default), `"mmr"` and `"similarity_score_threshold"` (filter by score). Retrievers can also wrap non-vector sources. The next step is a RAG app that combines question and retrieved context in a prompt.

The Meridian code compares with this directly: it uses the same splitter with 1,000-character chunks and 100 overlap, and its three retrieval strategies are functions built on the same retriever idea.

## Common mistakes

| Mistake | Symptom | Fix |
| --- | --- | --- |
| Embedding dimensions not matching the index | Indexing or search errors | Use a 768-dimension embedding model |
| Re-embedding with a different model but keeping old vectors | Meaningless scores | One model must index and search; re-index everything |
| Throwing away the original files | Cannot re-index after a change | Keep the originals |

## Interview corner

:::qa Why do chunks overlap?
So a sentence cut at a chunk boundary still appears whole in the neighbouring chunk. Meridian uses chunks of about 1,000 characters with 100 characters of overlap.
:::

:::qa What breaks if the embedding model's output size differs from the index?
Indexing or search fails: the index expects 768 dimensions, so the embedding model must output 768.
:::
